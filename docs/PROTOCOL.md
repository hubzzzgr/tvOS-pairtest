## Discovery and identity

System DNS-SD (`NetServiceBrowser` / `NetService`) browses `_remotepairing._tcp`, `_remotepairing-manual-pairing._tcp`, `_apple-mobdev2._tcp`, and `_remoted._tcp` in `local.`. These four types, plus the explicitly published pairable-host type, are declared in Info.plist. Adds/removes are live; TXT monitoring and fresh resolution every 15 seconds update metadata and addresses. Resolution includes numeric IPv6 interface scopes. Each service is a separate row, avoiding unsafe grouping by display name. No advertisement authenticates an Apple TV. Model TXT metadata is labeled unverified; outbound PIN setup requires an AppleTV model in the actual pairing handshake. The regular service is treated as a saved-record endpoint, not a new-pairing entry point.

`DiscoveryHealth` tracks active searches, service-specific failures and successful observations independently. `-72008` from one browser is not interpreted as a blanket permission denial. A successful observation suppresses that global warning even if another search subsequently fails. Stale callbacks from stopped browsers are ignored. Each error is logged with its actual service and a structured DNS-SD error code.

Manual IP/hostname entry requires a user-supplied port and protocol hint. TCP readiness proves name resolution plus transport connectivity only. Errors or no results do not establish that a TV is absent. DNS-SD policy denial is explained, and network-path status is not treated as Local Network permission status.

## Pairing control plane

`RemotePairingClient.swift` implements bounded RPPairing framing: ASCII magic, two-byte big-endian JSON length, host/device envelope, sequence number, base64 TLV bytes. It validates received magic, shape, device origin, TLV bounds/state, and frame limits; raw payloads never enter logs. The initiating client requests wire version 19 and checks whether it lies within the peer's advertised minimum/maximum range; a maximum of 26 is not rejected merely for differing from 19. Disjoint or malformed ranges stop explicitly.

## Device-initiated iPhone / iPad onboarding

`PairableHostListener` opens a public Network.framework TCP listener and publishes `_remotepairing-pairable-host._tcp` with the reference TXT keys `name`, `identifier`, `authTag`, `model`, `flags`, `ver` and `minVer`. Publication requires an explicit user action, waits up to two minutes for one incoming device, and rejects additional connections during that session. `didNotPublish` errors identify this specific advertisement rather than implying that all browsing is blocked. LiveContainer's own Bonjour declarations can constrain the guest.

`PairableHostSession` implements the opposite protocol role to the Apple TV client: the incoming iPhone is the wire `host`; TVPair replies as the wire `device`. It advertises wire version 26 with minimum 19, rejects an incoming pair-verify request on this new-setup listener, and only displays a fresh six-digit code after receiving setup M1. The user enters the code on the other device. `SRPServerSession` checks the controller's M3 proof, sends M4, authenticates/decrypts M5, and verifies its Ed25519 controller identity signature before sending TVPair's signed/accessory identity in encrypted M6. The PIN is cleared after M3, cancellation or failure and never enters diagnostic events. No all-zero/pinless mode is offered.

The compatibility model identifier `Mac17,7` in the host advertisement/identity follows the MIT reference, which requires a computer model for this device UI. It is a synthetic protocol label, not a retrieved statement about the iPhone's hardware. The host's signing identity and advertisement key are generated for each explicit onboarding session. The new record stores the actual peer signing key and identity metadata. Since the reference iPhone Wi-Fi trust may be session-limited, the incoming control channel is kept open while the result is displayed. Dismissing the result stops it. Persistent device-side trust is not claimed.

After authentication, TVPair searches the normal discovered advertisements for the recorded peer identity tag, reconnects with full peer verification, then performs the existing trusted-tunnel/developer-service tests. Absence of a matching advertisement is reported explicitly after the record has been saved. Tests cover successful reverse-role setup, bad client proofs and bad peer signatures; those are synthetic protocol tests, not a physical iPhone/LiveContainer result.

New pairing sends the observed initial Pair-Verify exchange and `pairVerifyFailed` reset, then `setupManualPairing` M1. A received manual M2 challenge supplies salt and SRP server public value. After the UI supplies the PIN, SRP-6a uses RFC 5054's 3072-bit group, generator 5, SHA-512, username `Pair-Setup`, and the integer encoding checked against reference behavior. M3 sends A/proof; M4's server proof must verify. M5 signs host identity with Ed25519 and encrypts TLV/OPACK metadata using HKDF-SHA512 and ChaCha20-Poly1305. M6 is decrypted and its accessory identity signature verified before the record can be returned. Peer keys are pinned in that record.

Reconnect uses an ephemeral X25519 exchange, HKDF-SHA512, authenticated M2 peer-identity decryption/signature verification against the pinned key, host Ed25519 signature in M3, and an explicit successful M4. Descriptive `peerDeviceInfo`/`model` fields are optional for saved-record verification; an actual handshake response envelope is still required. The unauthenticated model is needed only to gate new Apple TV PIN setup. Failed verification never automatically repairs/replaces saved trust. Start a fresh PIN pairing explicitly.

The reconnect performed after initial Pair-Setup belongs to the tunnel test. `tunnelReconnectReporter` maps its intermediate TCP/handshake/authentication reports to a running tunnel check, preserving completed setup results and requiring TLS-PSK/CDTunnel before any tunnel success. A standalone saved-record attempt continues to report its own initiation and authentication checks normally. TCP-only tests explicitly mark later protocol checks as not attempted.

The native crypto implementation uses public CryptoKit/Security APIs. BigInt 5.7.0 supplies SRP modular arithmetic; it is variable-time and **not a hardened constant-time crypto implementation**. Tests cannot substitute for cryptographic review or hardware interoperability. Local identity metadata uses synthetic MAC/Bluetooth/serial values for the protocol envelope; these are never displayed as retrieved hardware facts. The PIN is never persisted or logged, but Swift strings do not provide guaranteed secure zeroization.

## Trusted channel and developer probe

After new Pair-Setup, the control connection is replaced by a fresh Pair-Verify session using the new record, since reference devices may close the setup connection after M6. `AdvertisementIdentity` checks regular-service TXT `identifier` / `authTag` with SipHash-2-4 and the recorded altIRK, following idevice's `peer_device.rs`; it uses the first six little-endian digest bytes in reverse order. Tests include published SipHash vectors. This is only an endpoint-selection hint; pinned peer-signature verification remains mandatory. A name match never transfers trust. If no matching regular advertisement is available, the selected endpoint is tried and a manual endpoint may explicitly reject tunnel creation.

After verification, `createTunnelListener()` sends a ChaCha20-Poly1305 encrypted `createListener` request, deriving directional main keys from the session secret. The returned port is validated. Users can select the regular advertisement and reconnect using the record after an unsupported manual-endpoint result.

Build 3's system TLS attempt stopped at its negotiated-suite check in the user's LiveContainer retest. Build 4 uses `PSKTLSTransport` with the bundled OpenSSL 3.6.5 engine from [OpenSSL-Package 3.6.5000](https://github.com/krzyzanowskim/OpenSSL-Package/tree/4ac3f9a68731cb3cf736a591814bad9a7a2008c8). Both package locks pin that revision; SwiftPM verifies the XCFramework ZIP checksum. This replaces the system TLS path rather than relaxing its success criteria. No private framework or entitlement is used.

The small `TVPairTLS` C adapter configures TLS 1.2 only, offers `TLS_PSK_WITH_AES_256_CBC_SHA384` (0x00AF) and `TLS_PSK_WITH_AES_128_CBC_SHA` (0x008C), and supplies the authenticated Pair-Verify secret through OpenSSL's per-connection [PSK callback](https://docs.openssl.org/3.6/man3/SSL_CTX_set_psk_client_callback/) with an empty identity. It disables session caching, tickets, compression and renegotiation. OpenSSL implements the TLS protocol, Finished verification, CBC authentication and padding validation. The adapter never implements its own TLS cryptography or accepts a different protocol/suite. PSK buffers in the C engine are cleansed on destruction.

Memory BIOs connect OpenSSL to the existing asynchronous public `NWConnection` TCP transport. A single Swift actor owns each TLS engine and rejects overlapping operations. Whole-operation deadlines, cancellation, input/output/read limits and encrypted-record bounds are retained. A TLS failure closes the transport with a numeric OpenSSL reason; no raw protocol payload, key, session dump or TLS error string enters diagnostics. The TLS Finished and CDTunnel steps have distinct progress messages. A separate OpenSSL command-line server is required in CI for loopback interoperability, both permitted suites, multi-record payloads, wrong keys, wrong suites, tampered ciphertext, read timeouts and cancellation. A valid authenticated TLS connection plus CDTunnel configuration is required to pass the tunnel check. A listener port alone is insufficient.

The negotiated TLS cipher is inspected before CDTunnel starts; connecting with any other suite cannot pass the PSK check. CDTunnel carries IPv6 packets. Merely dialing the returned tunnel IPv6 address with a normal system socket would assume a route that this no-VPN app does not install. Instead `TunnelTCPTransport` creates a single bounded userspace TCP stream over the reliable encrypted CDTunnel carrier, with IPv6 framing, checksum validation, MSS, SYN/ACK, cumulative ACKs, duplicate handling, and FIN. It has no LAN raw socket, TUN device, or kernel route. This limited diagnostic transport is not a general TCP stack: no IPv6 extension headers/fragmentation, SACK, window scaling, zero-window probes, or general retransmission engine. Unsupported cases and stalls are reported rather than treated as successful connections.

`RemoteXPCTransport.swift` implements the reference HTTP/2 preface, settings, root/reply channels, XPC wrapper/object encoding and bounded reassembly, SETTINGS/PING acknowledgements, and receive-window updates. `DeveloperConnection` sends the RSD handshake (stable record host UUID, protocol version 7) and reads actual `Properties` and `Services`. It probes native `com.apple.instruments.dtservicehub` using raw DTX, or the advertised CoreDevice deviceinfo endpoint using `com.apple.coredevice.feature.getdeviceinfo`. Native dtservicehub is not a lockdown shim and does not get an RSDCheckin exchange. A successful DTX handshake, deviceinfo channel and `runningProcesses` array are required for Instruments availability; an advertisement alone cannot pass. CoreDevice requires an output dictionary. Missing supported ports are blocked; an attempted but unsuccessful probe is failed, with a visible explanation. No developer image is mounted and no Developer Mode setting is changed.

RSD `DeviceName` is used when present. Otherwise a usable saved-record name may be displayed with **Name source: Saved pairing record**. Imported or locally stored metadata is not relabelled as a current RSD response. Missing names remain unavailable if neither source has a value. The result keeps the authenticated tunnel and service session alive until dismissed.

## Instruments transport and manual pause/resume

Build 5's physical iOS 27.0.1 retest reached the Instruments parser but failed at `Instruments auxiliary header`; pairing, tunnel and RSD device properties passed. Its decoder incorrectly required the entire first auxiliary word to equal `0x1F0`. Build 6 accepts the low-byte `0xF0` dictionary type with upper flag bits and the legacy capacity-hint envelope, following [idevice's auxiliary decoder](https://github.com/jkcoxson/idevice/blob/89702099f4d7552f704f93b4526756abda319ceb/idevice/src/services/dvt/message.rs) and cross-checking the [primitive wire-format description](https://github.com/doronz88/pymobiledevice3/blob/776d601cec83b894c3ad0eeee8ab4db375a46e4a/pymobiledevice3/dtx/primitives.py). The screenshot does not reveal the actual header word, so this fixes a demonstrated parser assumption without claiming the phone's exact encoding is known. Lengths must still match exactly, dictionary keys must be positional NULLs, arguments and nesting are bounded, and archives retain the class allowlist. Structural errors report numeric lengths/markers only; no raw message or process metadata is logged. Empty auxiliary buffers decode as null values.

`InstrumentsTransport` implements bounded 32-byte DTX headers, 16-byte payload headers, auxiliary primitives/keyed archives, contiguous fragment reassembly, capability notification, correlated replies and channel creation, with reference to idevice's MIT-licensed `services/dvt/message.rs` and `remote_server.rs`. Compression is declined during capability negotiation. Unsupported encodings fail explicitly. Foundation performs keyed archiving; decoding requires secure coding and permits only a fixed list of Foundation value/container/error classes. Peer error descriptions and userInfo are not displayed or logged; only numerical error codes leave the decoder.

The protocol methods `processIdentifierForBundleIdentifier:`, `suspendPid:` and `resumePid:` were checked against [pymobiledevice3's process-control interface](https://github.com/doronz88/pymobiledevice3/blob/master/pymobiledevice3/services/dvt/instruments/process_control.py). No Python implementation is bundled. TikTok's `com.zhiliaoapp.musically` and Instagram's `com.burbn.instagram` identifiers were verified with Apple's public lookup API. Their fixed Pause/Resume actions have no PID input or process-name substring matching.

Build 7 adds a separate, confirmed BackBoard termination action. After the read-only Instruments probe passes, it opens processcontrol, queries `runningProcesses` twice for exactly one `name == backboardd` with the same valid PID greater than 1, confirms `execnameForPid:` has final component `backboardd`, then sends fixed signal 9 via `sendSignal:toPid:`. This reply-bearing method follows the reference interface; the fire-and-forget `killPid:` selector is not used. Acknowledgement does not independently verify termination, and a graphical-session restart may disconnect before any reply. Device authorization failures are surfaced without bypass. This action does not accept arbitrary names, PIDs or signals and is never triggered automatically. No app launch, automatic monitoring or background freeze loop is exposed.

Each manual request opens the processcontrol channel, resolves the exact bundle twice, requires an unchanged PID in 2...Int32.max, then awaits the suspend/resume reply. PID 0/1, negative/out-of-range values, changed PIDs, cancellation before the action, false acknowledgements and remote errors prevent a successful test result. An acknowledgement is reported as a request acknowledgement, not proof of a frozen state. App Store app permissions are device-controlled. Manual test results do not overwrite the read-only availability checks. Closing the connection does not automatically resume an app; the result provides an explicit Resume action.

`TunnelPacketRouter` cooperatively dispatches packets for up to eight userspace TCP connections over one CDTunnel. While a stream waits, packets for another registered stream are buffered and acknowledged rather than discarded. Each stream retains its one-MiB buffer bound. There is no background reader, and overlapping tunnel reads fail explicitly. This is still a bounded diagnostic TCP implementation, not a general-purpose network stack or VPN.

## Record format

Export is an XML plist. The required `public_key` and `private_key` fields are 32-byte Ed25519 data, `identifier` is the actual persistent host signing identifier, and optional `alt_irk` is 16-byte peer metadata. These keys and types were checked directly against idevice's `RpPairingFile.to_bytes/from_bytes`. Additional `host_identifier` helps reference clients that support overriding their machine-derived host ID; `remote_unlock_host_key` is empty because this Apple TV client does not create a remote-unlock key.

TVPair extension fields are `tvpair_schema`, `tvpair_id`, `tvpair_device_name`, `tvpair_device_identifier`, `tvpair_product_type`, `tvpair_paired_at`, `tvpair_peer_public_key`, `tvpair_peer_identifier`, `tvpair_host`, and `tvpair_port`. Reference idevice parsing ignores unknown keys. Peer signing key/identifier extensions are needed for TVPair's strict peer verification. Imported IDs never overwrite an existing record. Export round-tripping preserves identity material, not a claim that the imported host is trusted.

pymobiledevice3's examined writer emits `public_key`, `private_key`, `remote_unlock_host_key`, and optional `alt_irk`, while its verify path uses a locally generated host identifier unless `host_identifier` exists. Consequently an old plist without its original host identifier cannot safely be imported by inventing one. TVPair rejects such a record until that identity is supplied in a compatible format. Older idevice plists carry `identifier` but lack the peer signing key; TVPair can store/export them but deliberately cannot authenticate their peer. This is **format-level comparison**, not an end-to-end interoperability claim. Hardware cross-tool reconnect/export tests remain outstanding.
